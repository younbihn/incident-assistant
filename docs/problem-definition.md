# 문제 정의서: 장애 대응 도우미

> 이 문서의 모든 수치는 합성 로그에서 측정한 값입니다. 실제 운영 데이터는 사용하지 않았습니다.

## 1. 배경
정보시스템 운영 중 장애가 발생하면 담당자는 세 가지 일을 순서대로 해야 한다.
(1) 여러 서비스의 로그에서 이상 구간을 찾고, (2) 무슨 일이 일어났는지 정리해 보고하고,
(3) 흩어진 대응 매뉴얼에서 해당 절차를 찾는다. 야간이나 초기 대응처럼 경험이 적은 담당자가
혼자 판단하는 상황에서는 이 세 단계가 모두 오래 걸리고 결과가 담당자의 숙련도에 좌우된다.

## 규모 감각
- 이 프로젝트의 합성 로그는 7,090줄이고 1분 단위로 집계하면 1,433행이다. 그중 이상으로 표시된 구간은
  115분이고 사건으로 묶으면 4건이다. 7,090줄을 읽는 일이 사건 4건을 읽는 일로 줄어든다.
- 운영 현장의 장애 한 건은 로그 확인과 초기 판단에 수십 분에서 수 시간이 걸리는 것으로 기억한다
  (경험에 따른 추정이며 측정값이 아니다).

## 2. 문제
1. 로그 양: 서비스 4개, 6시간 로그가 7,090줄이다. 사람이 눈으로 훑어 이상 구간을 찾기에는 많다.
2. 에러 없는 장애: 에러율 기준 규칙은 오류 없이 느려지는 유형을 구조적으로 놓친다.
   측정: 규칙 재현율 0.74 (시드 5개 평균 0.76), 놓친 구간이 모두 이 유형이었다 (시드 5개 모두).
3. 매뉴얼 탐색: 담당자가 쓰는 말과 매뉴얼의 표현이 다르다. 띄어쓰기 기준 단순 검색은
   상위 3개 안에 정답 문서가 들어오는 비율(Recall@3)이 0.60에 그쳤다.
4. 요약의 신뢰: LLM 요약은 그럴듯하지만 근거 없는 내용을 지어낼 수 있다.
   근거 없는 요약은 운영 판단에 쓸 수 없다.

## 3. 사용자
- 야간 또는 초기 대응을 혼자 맡는 운영 담당자
- 장애 대응 경험이 적은 신규 운영 인력

## 4. 목표와 비목표
목표
- 이상 구간을 정답 라벨과 비교해 측정 가능한 방식으로 찾는다.
- 사건 요약에 근거 로그 번호를 달게 하고, 번호가 실재하는지 자동 검사한다.
- 사건 증상에 맞는 대응 절차를 찾아 보여 준다.
비목표
- 자동 복구, 실시간 스트리밍 처리, 실제 운영 시스템과의 연동
- 매뉴얼의 자동 생성, 모델 자체의 학습

## 5. 측정 결과 (합성 데이터 기준)
| 문제 | 접근 | 결과 |
|---|---|---|
| 에러 없는 장애 | 여러 지표를 함께 보는 IsolationForest | 시드 42: 재현율 0.74 -> 1.00, F1 0.80 -> 0.90, 대가로 오탐 10분 -> 21분. 시드 5개 평균(케이스 20건): 재현율 0.76 -> 0.97, F1 0.81 -> 0.86, 케이스 탐지 15 -> 20건 |
| 매뉴얼 탐색 | 글자 n-gram TF-IDF | Recall@3 0.60 -> 1.00 (평가 질문 10개) |
| 요약의 신뢰 | 근거 번호 인용 + 코드 검증 | 없는 번호와 무인용 답변을 모두 차단 |

## 6. 제약과 원칙
- 모든 로그와 매뉴얼은 합성이다. 실제 로그, 서버명, 기관 정보, 내부 매뉴얼은 사용하지 않았다.
- LLM 호출의 기본값은 외부 전송이 없는 Mock이다.

## 7. 한계
- 정답 라벨과 데이터를 같은 사람이 만들어 실제보다 낙관적일 수 있다.
- IsolationForest는 이상 비율(contamination)을 미리 가정해야 한다. 가정(8%)이 실제(4.1%)와 어긋난 시드 한 개에서 정밀도 0.51, F1 0.68로 규칙보다 낮았다.
- 인용 검증은 번호의 실재만 확인하며 근거의 타당성은 확인하지 못한다.
- 검색 평가 질문이 10개뿐이다. 뜻은 같고 표현이 다른 질문은 TF-IDF로 풀지 못한다.
