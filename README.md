# 장애 대응 도우미 (Incident Assistant)

> **합성 로그로 만든 데모입니다. 실제 운영 로그, 서버명, 기관 정보, 내부 매뉴얼은 코드에도 LLM API에도 사용하지 않았습니다.**

서비스 로그에서 이상 구간을 찾아내고, 장애 상황을 LLM으로 요약하고(근거 로그 번호 인용 + 자동 검증), 대응 매뉴얼(런북)에서 관련 절차를 찾아 주는 도구입니다.

```
로그(jsonl) → 1분 집계 → 이상 탐지 → 사건으로 묶기 → LLM 요약 + 인용 검증
                                              └→ 런북 검색 (TF-IDF)
                                  전부 Streamlit 화면 한 장에 표시
```

## 빠른 시작

Python 3.13.18에서 확인했습니다. 다른 버전은 확인하지 못했습니다.

```bash
git clone https://github.com/younbihn/incident-assistant.git
cd incident-assistant
python3 -m venv venv
source venv/bin/activate
pip install -r requirements.txt

python src/generate_logs.py     # 합성 로그와 정답 라벨 생성 (data/ 폴더)
python src/detect.py            # 이상 탐지 두 방식 비교
python src/summarize.py         # 사건 요약 + 인용 검증 (기본: mock)
python src/runbook.py           # 런북 검색 평가
python src/evaluate_seeds.py    # 시드 5개(장애 케이스 20건)로 탐지 성능 재측정 (약 1분)
streamlit run app.py            # 화면 (http://localhost:8501)
```

`data/` 는 스크립트가 만들기 때문에 저장소에 포함하지 않습니다 (`.gitignore`).

실제 LLM으로 요약하려면 합성 로그에서만 다음처럼 실행합니다. 키는 환경변수로만 전달하고 파일에 적지 않습니다. 이 경로는 아직 제 환경에서 검증하지 못했습니다.

```bash
pip install anthropic
export ANTHROPIC_API_KEY="..."
LLM_BACKEND=anthropic python src/summarize.py     # 모델은 LLM_MODEL 환경변수로 바꿀 수 있습니다
```

## 구성

```
app.py              Streamlit 화면
src/generate_logs.py  합성 로그 생성 (장애 4종 주입, seed 고정, 시드를 인자로 바꿀 수 있음)
src/detect.py         1분 집계, 규칙 기반 vs IsolationForest, 정답 대조 평가
src/evaluate_seeds.py 시드 5개 평가, 임계값 비교
src/false_positives.py 오탐 분석
src/min_requests.py   "요청이 적은 분은 판단하지 않기" 실험
src/summarize.py      사건 묶기, 프롬프트 조립, LLM 호출(mock/실제), 인용 검증
src/runbook.py        런북 청크 분할, TF-IDF 검색, Recall@k 평가
runbook/              합성 런북 6개 (직접 작성한 일반 지식, 실제 매뉴얼 아님)
```

## 측정 결과

합성 로그 7,090줄(4개 서비스, 6시간), 심어 둔 장애 4건, 시드 42 한 번의 결과입니다. 여러 시드의 결과는 아래에 있습니다.

| 방법 | 정밀도 | 재현율 | F1 | 비고 |
|---|---|---|---|---|
| 에러율 규칙 (30% 초과) | 0.88 | 0.74 | 0.80 | 놓친 24분이 모두 에러 없이 느려지는 유형 |
| IsolationForest | 0.82 | 1.00 | 0.90 | 오탐 21분 (짧은 잡음) |

| 런북 검색 방식 | Recall@1 | Recall@3 | 어휘 수 |
|---|---|---|---|
| 단어 기준 TF-IDF | 0.50 | 0.50 | 297 |
| 글자 n-gram (2~4) | 0.70 | 1.00 | 2178 |

단어 기준은 평가 질문 10개 중 4개에서 질의와 겹치는 단어가 하나도 없어 검색 결과가 비었습니다(조사가 붙은 한국어 표현 때문). 점수 0점인 조각은 결과로 치지 않습니다. 0점끼리의 순서는 의미가 없어, 포함하면 컴퓨터에 따라 우연히 맞은 것이 성공으로 세어집니다.

사건 요약은 4건 모두 인용 검증을 통과했습니다. 단, 기본값이 mock 이라 이 숫자는 파이프라인이 연결되었다는 확인이지 요약 품질의 증거가 아닙니다.

## 여러 시드에서의 측정 (장애 케이스 20건)

위의 표는 시드 42 한 번의 결과입니다. 한 번의 결과가 우연이 아닌지 보려고 시드마다 장애의 위치와 길이를 바꿔 5번(시드 101~105, 장애 케이스 20건) 다시 쟀습니다. `python src/evaluate_seeds.py`로 재현됩니다.

| 방법 | 평균 정밀도 | 평균 재현율 | 평균 F1 | 장애 케이스를 한 분이라도 잡은 수 |
|---|---|---|---|---|
| 규칙 기반 (에러율 30%) | 0.88 | 0.76 | 0.81 | 15 / 20 |
| IsolationForest | 0.79 | 0.97 | 0.86 | 20 / 20 |

- 시드 42의 F1 0.90은 평균 0.86보다 좋게 나온 시드였습니다. 단일 시드의 숫자를 그대로 일반화하면 안 됩니다.
- 모델이 항상 낫지는 않았습니다. 시드 101에서는 IsolationForest의 F1이 0.68로 규칙(0.79)보다 낮았습니다. 원인은 `contamination=0.08`이 "전체의 8%가 이상"이라는 가정인데 이 시드의 실제 이상 비율은 4.1%였기 때문입니다(시드별 4.1%~8.8%). 가정이 실제보다 크면 정밀도가, 작으면 재현율이 떨어집니다.
- 규칙이 놓친 5건은 모두 오류 없이 느려지는 `slow_degradation`이었습니다.
- 규칙의 임계값을 0.5로 올리면 F1이 0.83까지 올라 모델(0.86)과 차이가 작습니다. 다만 이 임계값은 같은 시드들을 보고 고른 것이라 규칙에 유리하게 잡힌 값입니다. 모델의 `contamination`은 시드 42에서 정했기 때문에 이 5개 시드는 처음 보는 데이터입니다.
- 화면에 보이는 사건 목록은 시드당 4~5건이었고 정답 장애 4건을 모두 포함했습니다. 가짜 사건은 시드 두 개에서 1건씩 나왔고, 시드 105에서는 장애 하나가 두 사건으로 쪼개졌습니다.

## 오탐 분석 (시드 42)

IsolationForest의 오탐 21분과 규칙의 오탐 10분은 모두 장애 구간에서 2분 넘게 떨어진 곳에서 나온 잡음이었습니다. 정상 구간의 평균 요청 수는 서비스 하나당 분당 약 5건이라 표본이 매우 작습니다.

- 규칙의 오탐 10분은 전부 에러율이 튄 경우였고, 분당 요청이 1~3건뿐인 분이 9분이었습니다. 예를 들어 요청이 1건인데 그 1건이 5xx이면 에러율이 100%가 됩니다.
- IsolationForest의 오탐 21분은 가장 튄 지표가 에러율 9분, p95 지연 7분, 요청 수 4분, 평균 지연 1분이었습니다.
- 가장 쉬운 해결책인 "분당 요청이 N건 미만이면 판단하지 않기"를 시험했습니다. N=3이면 오탐은 10분에서 7분으로 줄지만 놓치는 장애 구간이 24분에서 35분으로 늘어 F1이 0.80에서 0.74로 떨어졌습니다. 장애 구간도 분당 요청이 평균 약 5건이라 같이 걸러지기 때문입니다.
- 앞으로의 개선 후보는 1분 단위 대신 여러 분을 묶어 이동 창으로 보는 것입니다. 아직 구현하지 않았습니다.

## 설계 결정

- 탐지는 규칙과 모델을 모두 만들어 같은 정답 라벨로 비교했습니다. 규칙은 오류가 없는 성능 저하를 구조적으로 놓칩니다.
- 사건 묶기의 간격 허용치(2분)와 최소 지속 시간(3분)은 실험으로 정했습니다. 후보 24건이 4건으로 줄어듭니다.
- LLM 호출을 한 함수로 감싸 mock 과 실제를 바꿔 끼웁니다. 키 없이도 전체 흐름이 동작합니다.
- LLM 답변은 근거 로그 번호(`[L1]`)를 인용하도록 강제하고, 인용한 번호가 실제 있는지 코드로 검사합니다.
- 한국어 검색은 띄어쓰기 기준보다 글자 n-gram이 조사와 어미 변화에 강해서 기본으로 씁니다. 대가는 색인 크기입니다.

## 한계

- 데이터가 합성이고 정답 라벨도 같은 스크립트가 만들었습니다. 실제 로그에서의 성능은 알 수 없습니다.
- 인용 검증은 "번호가 실재한다"만 확인합니다. 그 로그가 주장을 뒷받침하는지는 확인하지 못합니다.
- 장애 4종류와 서비스의 짝은 고정이고 시드마다 위치와 길이만 바뀝니다. 새로운 유형의 장애에서의 성능은 알 수 없습니다.
- IsolationForest는 `contamination`(전체의 몇 %가 이상인가)을 미리 알려 줘야 하는데, 실제 운영에서는 이 비율을 알 수 없습니다.
- 검색 평가 질문이 10개뿐이라 숫자의 일반화에 한계가 있습니다.
- 의미가 같고 표현이 다른 질문(예: "윗선에 알린다" 대 "보고")은 TF-IDF로 풀지 못합니다. 임베딩이 다음 후보입니다.

## 데이터와 보안 원칙

- 모든 로그와 문서는 합성입니다. 실제 데이터는 저장소 어디에도 없습니다.
- `.env`, `venv/`, `data/` 는 커밋하지 않습니다. API 키는 코드에 적지 않습니다.
- 화면의 "실제로 보낸 프롬프트"에서 LLM에 전달되는 내용을 그대로 확인할 수 있습니다.
